    Release Notes¶

    A curated, reverse-chronological summary of user-facing changes in vornik. Each entry highlights what changed for you as an operator — new features, behavior changes, and notable fixes. Internal-only changes are omitted.

    Upgrading

    New configuration keys are additive and default to the previous behavior, so upgrades generally require no config changes. Always take a backup before upgrading. A few releases ask you to restart the daemon to pick up new behavior; those are called out below.

    2026.11.8¶

    Upgrade requirements

    • Tailnet addresses are now private. Vornik treats carrier-grade NAT, 100.64.0.0/10, where Tailscale assigns addresses, like a LAN range. An agent project's API or MCP server on a tailnet peer stops working until its host is on agent_admin.private_api_hosts, and its URL must be https. Before upgrading, add to that list the host of each agent connection on a tailnet (one whose host is a *.ts.net name or resolves into 100.64.0.0/10). For a connection whose URL is a 100.x address, list the address. After upgrading, vornikctl doctor reports agent_connections_cgnat as an ERROR naming each such connection still unlisted; list its host or remove the connection.
    • Other daemon clients lose tailnet reach with no list to restore it: an OIDC issuer, a broker URL or a Bedrock image URL on a 100.64.0.0/10 address is refused. A hub probe target there needs integrations.allowed_hosts. Self-hosted model endpoints keep their tailnet reach, and a model on a tailnet peer still needs its approval as a remote one. On a managed instance, a customer's own model endpoint on that range is refused, as a LAN one already was.
    • An approval waiting at the upgrade can be refused once. An agent's request to connect an API or MCP server now records whether agent_admin.private_api_hosts gave it intranet reach, and the apply refuses it if that changed after filing. A request filed before the upgrade records none, so if its host is on the list it is refused when approved, with "the operator's list of intranet hosts changed after you were asked"; the agent asks again and the new approval names the host.
    • A quickstart install keeps its old service unit until you replace it. The shipped unit is now Type=notify, so systemd waits for the daemon to report ready and a boot that hangs is restarted after 300 s instead of showing as running forever. The updater never rewrites your unit: an install made by an older quickstart keeps Type=simple, and the update warns and names the command. To get the bounded start, install the shipped unit: install -m 0644 deployments/podman/systemd/vornik.service ~/.config/systemd/user/vornik.service && systemctl --user daemon-reload (from your checkout).

    New features¶

    • An agent's jobs can share a memory, and a job can start the next one.
    • Before: each project an agent such as Hermes built for a job kept its own memory, which nothing else could read. The venue-scouting job's results never reached the enrichment job unless Hermes copied them by hand.
    • Shared memory, by opt-in: a project created or updated with shared_memory reads and writes the namespace's shared memory (<namespace>--home); you approve joining on your phone. Every other project's memory stays sealed, so a job that reads private data never feeds one that reaches the web.
    • Handover: a workflow can declare hand_over in define_workflow. When it completes, it starts another workflow of the namespace and hands it chosen output files as document inputs. You approve the hand-over on your phone. A loop is refused; a chain stops after three hand-overs from one delegation. Each attempt is counted on vornik_agent_handovers_total.
    • For the agent: describe_installation now lists the five ways to lay out projects (patterns), and the admin guidance and tool descriptions say the same.

    • The agent's own memory is unchanged: it stays where its memory key is. Existing job memory stays in each project; to keep it after a project joins the shared memory, move it with vornikctl memory reassign.

    • Start the daemon held, then release it. A start-held marker file in the data directory makes the next start serve its listeners without starting any work: no scheduler, autonomy, channel polling or task leases. /readyz answers 503 "status":"held" with its checks, so an upgrade can verify the new version before it touches anything. vornikctl daemon release reloads the config files, removes the marker and starts work; a release that fails stays held or exits, and the marker decides. A hold past its deadline (30 minutes by default) stays held, reports overdue and alerts once. While held, webhooks get 503. After a release the daemon redelivers the GitHub App deliveries that failed while it was held, up to 200, and GET /api/v1/daemon/hold reports how many it could not. On a managed instance, managed-upgrade now starts the new version held, checks /readyz and doctor, and releases it; a held version that fails those checks is rolled back before it has done any work.

    • Intranet hosts per project, by address, port or pinned addresses. An agent_admin.private_api_hosts item may now be an IP address (10.0.0.5, a 100.x tailnet address, IPv6) or carry a port (nas.lan:8443), which limits it to that port. An item may also be a mapping with host, addresses (the addresses or CIDRs the host may resolve to: anything else is refused, public or private) and projects (the agent projects it serves). Plain names keep serving every agent project; name projects when more than one exists. The approval names the host and any pins and records the grant; a restart that changes the grant before the approval applies makes the apply refuse. describe_installation lists the hosts an agent's projects may reach, and vornikctl doctor (agent_private_hosts_unused) warns about an entry no approved connection uses. A listed host's private reach now holds on the URL's own port only, and its client follows redirects to its own origin only: a server that redirected to another port or to plain http on itself is refused there.

    • Shipped roles name a model tier, not a model. The swarms and project templates Vornik ships no longer pin Bedrock or Ollama models. Each role names a tier instead (complex, coding, standard, trivial or vision), and every tier runs on your setup model until you map it. Map tiers in runtime.agent_llm.tiers, or apply a shipped provider profile with vornikctl models profile apply bedrock or ollama-cloud. vornikctl models tiers shows what each role runs on. Setup names the profile that matches your endpoint, and a managed instance sets tiers from its catalogue through setup/managed (operations API 1.6.0). An installed instance keeps its own swarm files, models included. Guide: Choose the models your roles run on.

    • opencode connects to Vornik in one command. vornikctl companion connect opencode checks a companion key and stores it in a file only you can read. It then writes into opencode's config directory:

    • an MCP entry that runs Vornik's bridge (no opencode config holds the key);
    • a plugin that adds Vornik's working rules and a session digest to the system prompt;
    • the companion skills, as skills/vornik-*. doctor --client opencode checks the install, and disconnect opencode removes it. Tested live with opencode 1.14.37. The plugin uses an opencode hook marked experimental, and doctor warns when your opencode version differs from the tested one. Guide: opencode.
    • The App review measures itself. A canary run gives the review a generated diff of planted fake secrets and decoys, then scores what it caught instead of posting. It posts nothing and calls GitHub for nothing. Schedule it weekly with autonomy's cron mode, and set floors after four measured runs; with no floors set it only reports. See Forge.
    • PR reviews read scanner results as SARIF. When your pipeline uploads a .sarif file as its CI artifact, a review shows one line per finding: level, rule, file, line and message. The App review's triager merges these with the reviewers' findings, and a finding still posts only on a line the pull request adds. Code snippets and fingerprints, which can hold the secret a scanner found, are never shown.
    • Cursor connects to Vornik in one command. vornikctl companion connect cursor checks a companion key, stores it in a file only you can read, and installs a Cursor plugin: an MCP entry that runs Vornik's bridge (no Cursor config holds the key), an always-applied rule with Vornik's working rules, the companion skills, and a session hook that adds your delegations and recent memory to a new chat. Tested against Vornik's companion endpoint as installed; not yet in a live Cursor session. Guide: Use Vornik from Cursor.
    • Autonomy can observe before it acts. With autonomy.observe: true, a project's autonomy loop runs as usual, records what it would have started (WOULD_START, with the prompt) and starts nothing. The project page counts the last 7 days' proposals and shows the latest five; vornikctl autonomy evaluations --outcome WOULD_START lists them all. New projects start in observe mode; existing projects keep acting, because an absent key means false. Guide: Observe first.
    • Each agent role can set how much its model reasons. reasoning: off | low | medium | high on a swarm role, or on a model's runtime.agent_llm.model_limits entry, is sent to the provider in its own form. A model that refuses the setting is retried once without it; a Bedrock model that refuses only off (GLM 5.3) gets low instead. vornik_chat_reasoning_requests_total{model, requested, applied} counts the calls on the OpenAI-compatible routes. Measured on Ollama Cloud glm-5.3-flash: off took a small answer from 41 to 6 completion tokens.
    • Each companion key has a request limit. A companion key may make 5 requests a second, with bursts of up to 50; past that the companion endpoint answers 429 with Retry-After. A leaked key or a client stuck in a loop no longer calls as fast as the daemon answers. Change or turn off the default with api.rate_limit.companion_key (rps, burst, off). A key whose own row sets a limit keeps it.
    • A GitHub Actions job can call the companion without a stored secret. Bind a companion key to one workflow with vornikctl companion trust-github; the job then authenticates with the ID token GitHub issues to its run. Every claim must match exactly (repository id and name, ref, workflow file, event, audience), and a run on another branch, a fork or a pull request gets a 401. vornikctl companion grant --oidc-only mints a key whose secret is never printed.
    • Secret findings in stored artifacts are counted. vornik_artifact_secret_findings_total{type, outcome} counts each one as rewritten, stored (detect mode) or dropped (a heuristic rule, which never rewrites an artifact), so you can see how often each rule fires.
    • Any agent that speaks MCP can use Vornik. vornikctl companion connect generic --print checks a companion key, stores it in a file only you can read, and prints the MCP entry to paste, never the key. vornikctl companion instructions --write AGENTS.md gives the agent Vornik's working rules. Measured on 2026-11-20: Gemini CLI and opencode each stored, recalled and refuted a note and delegated a task, in about 100 seconds; neither gets a session digest. Grant such a key with --repo-scope: without one, an agent with no Vornik hooks stores its notes unscoped. Guide: Use Vornik from any agent.
    • Task, execution and lease IDs are shown short in the console. Every page shows T-fee9, X-a1b2 and L-9c4d instead of the full ID, which took a line of its own on a phone. Hover over a short ID, or open its link, for the full one. Instincts (I-fee9) and control-plane proposals (P-fee9) are short too, and an approver device shows dev_… and its last 6 characters, as on the phone. IDs you chose (projects, workflows, swarms), a detail page's own ID, and data subject request and incident IDs stay whole.
    • setup/status reports a restart generation. pending_generation counts the settings saved that need a restart, and loaded_generation the count the running process started with. When they differ, a restart is still owed, even if one already happened while the change was being saved. Operations API 1.5.0.

    Fixes¶

    • A re-run of an incomplete erasure, rectification or restriction keeps every run's report. A re-run used to overwrite the first run's stored report, so after it nothing recorded what the first run had erased or corrected. The stored report now keeps the latest run at the top, plus the run number and every earlier run's report, oldest first. A report stored before this release reads as run 1.

    • vornikctl memory recheck-urls never probes a private or metadata address. It kept its own list of private addresses, which missed a cloud metadata address and several encoded forms of blocked addresses, so it could learn whether hosts at those addresses were alive. It now uses Vornik's one list of private addresses, checked before the request, at each redirect and at connect time.

    • An oversized OIDC key set is named in the log, not cut off silently. A key set over 1 MiB used to be truncated, so every GitHub Actions token was refused with only a JSON parse error as the logged cause. The log now says the key set is over the 1 MiB cap. Tokens are still refused, as before; only the reason changed.

    • The skill distiller treats recalled memory as untrusted. A step that only searched memory was accepted as safe, so web text that had reached project memory could feed a distilled skill. Such a step is now judged by what its searches returned: fetched web content, or anything the distiller cannot check, keeps it out of a skill.

    • A model is checked before it is saved. Saving a role's model or a tier mapping now makes one live test call through the instance's router (15 s timeout). A model that does not answer is refused with the provider's reason and nothing is written; one that answers without tools is saved with a warning. On a managed instance, a model outside the instance's catalogue is refused everywhere it can be saved, and a step that resolves to one fails before its container starts.

    • The doctor reports a retired model at once. A model that answers HTTP 410 used to show only through a failure rate, after enough calls, and the message did not say it was gone. model_calls_live now lists gone models first, with no minimum number of calls, and names each role that still points at one.

    • The adaptive router sees the project's workflows, and one "none" is not final. The router was not shown the candidate workflows with their descriptions, so it could misjudge, and a first "none" failed the task. Its prompt now lists every candidate with its description, and a first "none" gets one corrective retry; a second "none" still fails as ROUTE_NO_FIT.

    • Autonomy's first evaluation after a restart waits for the leader election. It used to run before the election had started, so a due evaluation could be refused after its model call was already paid for, and a replica without the lease ran it too. It now runs after the election, on the leader only.

    • A run_workers: false node runs no leader-only work. Such a node used to act as if it were always the leader, so a UI node could run the autonomy loop and the retention sweeper beside the worker node. Retention now deletes only from worker nodes. Single-node installs are unchanged.

    • Autonomy proposals follow a retention window. Rows recording autonomy's decisions were never pruned, and a proposed task's prompt can name a person. They now expire with the tool-audit window (tool_audit_days), and vornikctl retention shows them as autonomy_evals. The record of processing lists them as autonomy proposals.

    • The doctor's retention check states the defaults that apply. With retention on and no window set, it said the sweeper prunes nothing. In fact the compiled defaults apply: tasks, executions and artifacts after 60 days, LLM usage and chat audit after 90, tool audit after 180. The check now lists them, names the data with no default (memory chunks and task messages), and still warns, because the defaults were not chosen for your purposes.

    • Healing can repair a shared workflow, and a one-model install is told why it gets no candidates. A healing request could not read a workflow outside the project's own files, so it answered "the file does not exist". It can now read and propose an edit to the workflow its trigger names; the edit still needs a passing trial and your promotion. When the config assistant and its judge share a model, every candidate is refused; a new doctor row, healing_judge_family, and a start-up warning now say so and name config_assistant.judge_model.

    • A healing replay keeps its link to the task it replays. The link was written before the replay's execution existed, so it was lost on every replay and a warning fired each time. It is now written when the execution starts.

    • Instincts learn from real tool errors, and work on SQLite. A tool call was counted as failed whenever its output contained a word like "error", so reading source code counted as a failure and tool-swap instincts were learned with no counter-evidence. Only an error the daemon observed now counts, and a swap in a failed step counts against the instinct; the instincts learned by the old rule are retired. On SQLite, budget instincts could not be stored at all; the table is rebuilt once to accept every kind.

    • An agent that rewrites a file with the same content is told nothing changed. Such a write used to answer "wrote N bytes", and the model wrote again until the loop detector stopped it. It now writes nothing and says the file already holds exactly that content.

    • A failure caused by the output cap is no longer reported as a missing role. The failure explainer matched the word "role" in the output-cap message's advice and showed the missing-role remedy. It now matches only the messages a missing role produces.

    • vornikctl treats a command run from automation as non-interactive. Four commands mistook /dev/null for a terminal: auth login printed a typing hint, agent connect --api-key-stdin refused an empty key, init project printed prompts, and daemon operations-credentials refused to write to /dev/null. Each now checks for a real terminal.

    • A failed web chat reply no longer shows the error text. When a reply failed before any words appeared, the chat page showed "Chat dispatch failed:" and the raw error, to every viewer, including project members who are not operators. That error can carry the model provider's response, its address or part of a key. The page now shows the same notice Telegram does ("Sorry, I could not answer: the model call failed. Please try again."), and the error goes to the daemon log.

    • Slack says when it could not answer. A Slack message whose reply failed got no answer at all; the error went only to the daemon log. Slack now posts the same notice as Telegram and the web chat, where the answer would have gone, at most once per conversation per hour. It never shows the error text. A failed /vornik command gets the notice at channel level, where its answer would have posted. Notices are counted on vornik_channel_failure_notices_total{channel="slack"}.

    • A tool result the output guard cannot scan is withheld visibly. If the scanner failed, the model already got an empty result instead of the unscanned text, but nothing was logged and the code said the opposite. The model is now told the result was withheld, the turn carries a scan_failed guard warning, and the failure is counted on vornik_dispatcher_output_guard_scan_panics_total.

    • A hand-over finds the file the first job wrote. Vornik stores each output under a dated name (enrich-20261125-a8f2.md), and the hand-over looked for the plain name (enrich.md), so every hand-over was refused with "the job finished without" the file. It now matches the name the job wrote.

    • An assistant's hand-over request no longer fails after you approve it. An assistant could name a hand-over file by its bare name (enrich.md), the form a workflow's output list uses. Vornik showed the request for approval and then refused it while applying it, so the phone said "Could not be applied". A bare name is now completed to artifacts/out/enrich.md, and any other path that cannot be applied is refused when the assistant asks, before it reaches your phone.

    • A benchmark batch that could not be verified is re-run, not skipped. A step that failed before its container started was read as a run with no image identity, so its batch could not be verified and the pass stopped at its end. Such a step is no longer counted as a run, and a batch whose journal cannot be verified is re-run on resume.

    • A rejected healing candidate no longer blocks the next one. A workflow can have one pending proposal at a time. Rejecting a candidate left its proposal pending, so every later candidate for that workflow failed with "workflow already has a pending proposal". Rejecting a candidate now rejects its pending proposal too. The benchmark autopilot rejects a candidate whose trial failed.

    • The config assistant retries once when its reply is cut off. A reasoning model can spend its whole output budget thinking and never answer. The assistant now asks again once, one reasoning level lower (high to medium, medium to low, low to off), and refuses ASSISTANT_REPLY_TRUNCATED only if the retry is cut off too.

    • Every workflow step sees every earlier step's files. A step was handed only the previous step's artifacts/out/ files, while workflows built through the admin tools tell each step that earlier steps' files are there. In a four-step workflow, step 4 could not read what step 1 or step 2 wrote. Every later step now receives them; a file a later step rewrites is handed on in its newest version. An automatic resume restages the files of every step it carries over.

    • A workflow resumed after a pause still has its earlier steps' files. After an approval, a wait for child tasks or a daemon restart, the next step started without the files the steps before the pause had written. It now finds them, as an uninterrupted run does.

    • A git command stopped at its time limit takes its child processes with it. Vornik killed only git, so a transport or index-pack it had started could keep running, hold the command open and keep writing in the repository. Vornik now stops the whole process group. Git's own background maintenance is left alone, as before.

    • Telegram task control:

    • /inbox points each task to /status <id>. Before, it pointed to /task, which does not exist.
    • The assistant's own retry re-queues a task the way /retry does: atomically, failed, cancelled or completed alike.
    • The assistant can no longer cancel a task that is waiting for your approval; answer the approval instead.

    • A database error is no longer quoted in a reply; the reply says the action could not be done right now.

    • An agent's API call says when the API answered with an error.

    • Before: query_api handed a workflow role only the API's response body. A redirect or error with an empty body reached the role as an empty result, so a role reported "no results" for a call that had failed. list_apis showed only the API's host, so a role could not tell that the base URL already included a path such as /res/v1, and repeated it.
    • Now: an answer that is not a 2xx starts with HTTP <status> from provider "<name>".. A redirect also says that query_api does not follow redirects and that paths are relative to the base URL. list_apis shows an agent API's full base URL, path included.

    • What you might see: error answers in a role's tool results now carry this first line. Successful answers are unchanged.

    • A model endpoint counts as local only when Vornik can reach it (security).

    • Before: an agent model endpoint whose address was an IPv6 form carrying a private IPv4 address (NAT64, 6to4, IPv4-compatible), or a link-local address, counted as local. It skipped the device approval a remote model needs, and every call to it was then refused.

    • Now: an endpoint is local only when the model guard admits it: loopback or a private LAN address. Those shapes now count as remote and need an approval; calls to them are still refused.

    • The configuration assistant reports a cut-off reply instead of "no change".

    • Before: a reasoning model that spent its whole output budget thinking returned an empty reply. The assistant read that as its final answer and refused with NO_CHANGE and no reason. Self-healing counted that as a producer failure, the same as a timeout.

    • Now: a reply cut off at the output-token limit is refused as ASSISTANT_REPLY_TRUNCATED, naming the tokens spent and the remedy. A NO_CHANGE carries the assistant's reason, or says it gave none, and self-healing answers it with 422 HEALING_NO_CHANGE: the assistant found nothing to fix. The new config_assistant.reasoning (off, low, medium, high) sets the reasoning level asked of the assistant's model on every call.

    • vornikctl doctor exits 0 when the only non-OK checks are SKIPPED.

    • Before: a SKIPPED check, such as a feature that is not wired, made the command exit 1, although its summary listed no issue. Scripts read that as a failure.

    • Now: it exits 0 when every check is OK or SKIPPED, and 1 when any check is WARNING, ERROR or an unknown status. --json still exits 0 and --offline still exits 1 on a failed check.

    • Every address guard refuses what the daemon's guard refuses (security).

    • Before: A2A webhooks, companion push and the scraper kept their own lists of private addresses. Each admitted some address the daemon's dial guard refuses: 0.0.0.0/8, 255.255.255.255, multicast (the scraper's image and calendar fetches), and IPv6 forms that carry a private IPv4 address, such as 64:ff9b::a9fe:a9fe (169.254.169.254 through a NAT64 translator). A companion push range opened with companion_push.allowed_cidrs also reached the cloud metadata address inside it (100.100.100.200, fd00:ec2::254, fd20:ce::254).
    • Now: each guard decides by the daemon's one list, and an allowed_cidrs range never opens a metadata address. The scraper's encode_image and ical_events, and the web_fetch check before a page loads, refuse the same ranges as web_submit: also documentation, benchmarking and reserved addresses, and every NAT64, 6to4 and Teredo address.

    • What you might see: a push, webhook or scraper fetch to such an address now fails with a refusal. No supported target uses one.

    • A config change that fails to apply no longer hides a bad reload.

    • Before: when an approved change failed, Vornik reverted the files and reloaded, but it ignored that reload's result, and no reload had a time limit.
    • Now: every reload the control plane makes is bounded at 10 seconds. One that fails, times out or is stuck is logged and shown by vornikctl doctor (control_plane_restore_reload), with the remedy: fix the file and reload, or restart.
    • A reminder that cannot be delivered retries, then says so.
    • Before: a reminder whose send failed stayed "firing" forever. It was never delivered, never retried and never reported.
    • Now, a text reminder is tried three times: at its time, one minute later, and five minutes after that. Then a one-shot reminder becomes expired with its last error, and a recurring one moves on to its next occurrence.
    • A scheduled-task reminder is not retried, because a retry could start the task twice.

    • To find them: vornikctl doctor lists reminders that expired undelivered in the last seven days (reminders_undelivered).

    • CI artifact content reaches a review as text, masked. GitHub serves an artifact as a ZIP.     • Chat: a running turn can be stopped and steered. In Telegram, /stop ends what the assistant is doing in that chat and lists the tasks it had started; /stop tasks cancels those too. A message you send while your own turn runs now joins it at its next step ("Got it, I'll take that into account."), instead of waiting until the turn ends; in a group, another member's message still waits and runs as their own turn.
    • Chat: one status line instead of a line per tool call. A turn shows one line, edited in place above the reply, with the current activity, the time so far and a count per activity, and removes it when the answer lands. Slack's placeholder shows the same line.
    • Chat: long work is scheduled as a task. The assistant now treats research across several sources, multi-step work or a written document as a task in a project that can run it, and answers in the chat only what one or two lookups settle. It makes at most 4 web or consult lookups in one turn, and no longer polls task status in a loop. The project list it sees names what each project can run, so it picks a project by capability, not by a name that matches the topic.
    • Chat: smaller prompts on long conversations. Large tool results the model has already used (from earlier turns, or older than the turn's two newest tool steps) are sent shortened to their first 1,600 characters. A typical five-call turn sends about 40% less to the model; saved conversations keep the full results.
    • Chat fails over when the model is out of quota (fix). chat.model now routes by its model prefix like every other model call, so setting a Bedrock model as chat.model reaches Bedrock even when chat.router.default names another provider. A reply answered by the backup model says so in one line. The new doctor check chat_model_fallback warns when chat.model has no backup in chat.router.model_fallbacks, or one on the same provider.
    • A routed task that fits no workflow says so (fix). The adaptive router may now answer that none of the project's workflows fits; the task fails at once with ROUTE_NO_FIT, naming the project's workflows and what the task needs, instead of being forced into the closest misfit. Take the route prompt change into a deployed configs/workflows/adaptive.md (config_template_drift lists it); the router works without it.
    • The doctor no longer reads the routing model as always failing (fix). A route step that handed its task to a workflow was never recorded as a success, so vornikctl doctor reported the adaptive router's model at a 100% failure rate and advised switching it. A step that delegates is now recorded ok; the warning clears within a day of upgrading.
    • A task whose subtasks were all cancelled ends CANCELLED (fix), and its completion notice reports that, instead of reporting success.
    • Output a person can review (new). Every agent is told how to write for a person: answer first, short sentences, exact references, no unstated hedges. A swarm or a single role can switch this off with suppressedGuidanceBlocks (writing-style). The doc, architectural and GitHub review workflows report readability findings, each with the quoted passage, a problem class and a rewrite that keeps every fact. A review can withhold approval when its subject cannot be reviewed in reasonable time. A new system step, text.readability, measures words, sentence length, hedges and vague references. Its word lists are English only. On one deployment, 20 architecture reviews before and 20 after: mean sentence length fell from 17.1 to 10.0 words.
    • Approval notifications on the phone (new). A paired approver device can turn on browser notifications at /ui/approve/push, so an install with no chat or e-mail alerts still hears of a waiting request. A notification says only that a request is waiting, never what it asks, and is encrypted to the device. It needs an https public origin. On iPhone and iPad it works only from a Home Screen web app (iOS 16.4 or later).
    • Companion hints (new). GET /api/v1/companion/hints serves the project's hint catalogue to companion keys, and two project settings turn hints off or mute single ones (companion.hints, companion.mute). The daemon also records, per project, whether each hint was followed, and turns off for 14 days a hint followed in fewer than 2 of its last 10 firings. vornikctl companion hints -p <project> lists each hint's state and follow rate. The Claude Code (0.50.3) and Codex (0.45.1) plugins show the hints: after a commit, after a design edit, and after a failed test run, each at most once per session. Codex recognises a failed test run from its output, since it gives hooks no exit status.
    • Repository paths can be mirrored into project memory (new). A project can list repository paths whose documents are ingested into its memory and kept current; a document is mirrored only if its disclosure mark allows it, and an unreadable or partial mark fails closed.
    • A project key given to an A2A caller can no longer read the project's memory or keys (security). Before, a key narrowed to one workflow was still a full key on the REST API of its project.
    • Add MCP tokens without a shell. A secret://NAME reference now resolves from the daemon's environment, then from credentials you enter on Admin → Keys & access → Credentials (/ui/credentials) or type in the control plane's MCP form. Values are stored encrypted, never shown again, and every change is audited; saving registers a server that was waiting for its token, with no restart.
    • The updater shows what to do before an upgrade (fix). vornik-update.sh prints the "Upgrade requirements" of every release between the installed one and the target, read from the target's notes, before it changes anything. It continues only after you type the target's name, or, with --yes, after --ack-upgrade-requirements=<target>. --check prints them too.
    • Companion plugins work behind Cloudflare (fix). The Claude Code plugin (0.48.1) and the Hermes plugin (0.22.2) name themselves on every call, as vornik-companion/<version>. Python's default signature was refused by Cloudflare with error code: 1010, so /upload failed for a daemon behind it. A proxy or firewall in front of the daemon should allow that name.
    • Every step that produces a result is readable by later steps (fix). ${outputs.<step>.<field>} now resolves for plan, spawn_project and a2a_call steps, not only agent and system. A step that runs again and fails no longer leaves its previous result readable.
    • A later agent step can read a system step's output (fix). A step prompt can now reference a system step's result with ${outputs.<step>.<field>}, for example ${outputs.fetch_diff.diff} in a review workflow's second agent step. Before, such a reference passed validation and failed every run with prompt reference unresolved, so only the agent step directly after the system step saw the diff. A value longer than 256 KiB is cut, and the prompt says so. The value is otherwise inserted as-is: wrap it in your own delimiters and tell the model it is data, because a pull request's author controls a diff's text.

    Upgrade requirements

    • A workflow whose retry.on names a deterministic error class no longer loads. retry.on may name only unclassified, llm_call_failed, container_start_failed, container_wait_failed, container_killed and context_timeout; the error lists them. The shipped workflows already name only these.

    • An MCP subscription by name only, with no matching server in config.yaml, is now withheld, and the doctor's mcp_project_connections row reports it as a warning.

    Security fixes from an external scan, and safer quickstart defaults. An external scan of a deployment found three real problems:

    • GET /api/v1/config returned admin.allowed_keys and the S3 access_key_id values in plaintext to an operator-scope caller. The dump redacts by key name and these names matched none of its rules. They are redacted now, and a test checks every credential-shaped config field. What it does not cover: a secret stored under a name that contains none of key, pass, secret, token, cred or private.
    • The configuration assistant could pass a secret-named list (api_keys:, allowed_keys: written as a literal list in a project file) to the model. Such lists are now redacted whole, including lists of lists and lists of maps; a list of ${VAR} references stays editable. A secret reached through a YAML alias (api_key: *tok, with the value defined under a harmless key) also passed; the assistant now refuses to read such a file until the value is inlined or moved to ${VAR}. It also refuses a YAML file with more than one --- document, whose later documents were never screened.
    • /ui/static/, which is public so the login page can load, served a list of its files. Directory requests now return 404; the files themselves stay public.

    The quickstart seed (also used by the Lima and macOS installers) listened on all interfaces with auth off. A fresh install now generates an API key into ~/.config/vornik/secrets/api.env (readable only by you) and requires it; log in to the UI with it, and source ~/.config/vornik/shell-env.sh for vornikctl. A fresh install also gets its own database password, but only when no database exists yet, so a re-run never locks you out.

    Browser-login sessions can use the console again. Since 2026.9.6 every action that changed something (pausing a task, rechecking a channel) was refused with 403 for a session logged in through the browser, because the console never sent its CSRF token. It does now, and the 403 names the real cause instead of blaming Basic Auth.

    Vornik as the broker for a front-end agent. A chat agent such as Hermes Agent can now hold no credentials at all: it delegates to workflows you write in a project marked broker: true, passes typed inputs, and reads back only one declared, schema-checked result document. Raw task content stays inside Vornik. A broker workflow can also propose a write (a mail reply, say); you approve it in /inbox, and Vornik executes exactly the arguments you approved, once, with no model in between. Writes are off until you set broker.writes: on. result can wait up to 25 seconds for a task to finish, and a harness with a webhook can be pushed task and action states instead of polling. vornikctl companion grant --no-delegate mints a memory-only key that cannot start tasks. The Hermes plugin in contrib/hermes-companion/ is at 0.2.2; earlier READMEs named the memory provider vornik, which selects nothing — it is vornik-companion. See the companion guide.

    Agents stop spending tokens on work that cannot change the result.

    • The adaptive router step gets no tools and a fixed answer format. It used to be offered tools, and a correct first answer was re-prompted into exploring the workspace.
    • The retry ladder re-runs only transient failures. A schema violation used to be retried with identical inputs.
    • The prompt-token budget leaves room for the final answer instead of stopping a step after its research and losing the work.
    • A tool result enters the conversation capped at 32 KiB, with the full output kept for tool_result_read, which can now page through it.

    MCP servers recover on their own. A project MCP server whose first connection failed (for example, its container was restarting) was dropped until the next restart, and every call to it failed with "not connected". It is now retried in the background, you are alerted if it stays down for 10 minutes, and the doctor's new mcp_project_connections row lists such servers. An unreachable server also no longer holds the API closed at startup, which closes the 2026.9.8 known issue; a step whose server is still starting waits up to 10 seconds for its tools.

    New. vornikctl package upgrade upgrades an installed extension package file by file and refuses, with every reason, if you edited or deleted anything it contributed. Each step that runs in a fresh (non-warm) agent container now records that container's memory peak.

    Fixes.

    • Opening a live task page no longer makes other open pages show finished steps as running again.
    • A config edit made while another reload was running is applied instead of silently skipped.
    • SQLite lease expiry and task update-time comparisons are exact; mixed timestamp formats made lease expiry wrong by up to a second and task update times compare wrongly by up to a day.
    • Chat replies no longer start with invented markers such as "[from your notes: not applicable.]"; the model had been copying them from its own earlier replies.
    • A fact you deliberately save to memory from chat or a companion needs three words, not 64 characters.
    • Secret findings in artifacts, webhooks, backlog deposits and container logs now appear in the task's scan history.
    • The spend page labels memory reranking instead of showing a raw value.

    Known issues.

    • Ingesting HTML or EPUB files through the companion's RAG-ingest workflow stores markup and archive bytes rather than the extracted text.
    • Deleting or retiring memory does not yet remove the knowledge-graph entities and edges that only that memory supported.

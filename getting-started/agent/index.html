    Install Vornik with your coding agent¶

    This page is for your coding agent: Claude Code, Codex, Cursor or any agent that runs shell commands. Ask it: "Install Vornik by following https://docs.vornik.io/getting-started/agent/". It runs each step below, checks the result, and stops when a check fails.

    Some steps stay with you:

    • Installing prerequisites. The installer may sudo-install missing packages, and loginctl enable-linger changes the system. Your agent asks you first (ground rule 1 below).
    • Your LLM key. You type it where the agent tells you. The agent never shows it in chat (ground rule 2 below).

    Every call below goes to your own daemon on localhost. Call setup/apply only on localhost, never through a public hostname: on an install with authentication off it answers any caller that reaches it.

    Paths such as deployments/podman/quickstart.sh are in the public repository, github.com/EaseIT-cz/vornik. On macOS or Windows, follow https://docs.vornik.io/getting-started/ instead.

    This page is generated from the repository's AGENTS.md. Edit that file, not this page.

    Trust & safety (read first)¶

    • During install, Vornik doesn't send your data to us or any third party. Secrets are written to ~/.config/vornik/secrets/ and never transmitted.
    • Setup talks to your local daemon at http://localhost:8080. The outbound calls are ones you trigger yourself: validating your chat/LLM key against the endpoint you entered, and — if you enable memory/RAG — validating your embedding key against that endpoint. Never any Vornik service.
    • The installer is open source — review deployments/podman/quickstart.sh before running.

    Install (reviewable)¶

    curl -fsSL https://get.vornik.io -o quickstart.sh
less quickstart.sh          # review — nothing leaves your machine
bash quickstart.sh

    (One-liner curl -fsSL https://get.vornik.io | bash is the convenience option.) Note: the two-step path depends on get.vornik.io serving the current script; the in-repo deployments/podman/quickstart.sh is the reviewable source of truth.

    If a task fails after install¶

    1. vornikctl doctor — checks agent-LLM topology, workspace uid, upstream key, and more.
    2. vornikctl report — opens a pre-anonymized GitHub issue you review and submit.

    Upgrading from an install before this release¶

    The installer seeds ~/.config/vornik/configs/ only on first install (when it's empty) and preserves your existing configs on later runs — so an older ~/.config/vornik/configs/projects/dev-project.yaml keeps autonomy.enabled: true. If you don't want unattended scheduling, set it to false (or toggle it off in the UI). vornikctl doctor (autonomy_budget_guard) flags autonomy-enabled projects.

    Ground rules

    1. Ask before privileged commands. Package installs (sudo dnf/apt/…) and loginctl enable-linger change the system — surface them to your user before running. Everything else below is user-scoped.
    2. Never echo or commit secrets. LLM API keys and sk-vornik-* bearer tokens go only into the files named below, never into chat output, shell history you display, or git.
    3. Target platform is Linux with rootless Podman. On macOS/Windows, stop and point your user at docs/public/getting-started/index.md.

    Runbook A — zero → hello world¶

    A0. Check what is already here¶

    Before anything else, ask the local daemon whether Vornik is set up:

    [ -r ~/.config/vornik/shell-env.sh ] && . ~/.config/vornik/shell-env.sh
curl -sS http://localhost:8080/api/v1/setup/status -H "X-API-Key: ${VORNIK_API_KEY:-}"
    answer you
    connection refused (no daemon) continue with A1: nothing is installed
    200 with "fresh_install":true skip to A2: installed, not yet set up
    200 with "fresh_install":false stop: Vornik is already set up. Tell your user; to update it, follow Runbook D in AGENTS.md at github.com/EaseIT-cz/vornik
    anything else (401, 5xx) stop and show your user the response

    A1. Install the stack¶

    One command builds the daemon + CLI (in an ephemeral container — no Go toolchain needed), starts PostgreSQL + pgvector in a container, and runs the daemon as a rootless systemctl --user service. It may sudo-install missing prerequisites — warn your user first (rule 1):

    # Recommended for agents — verify the installer's checksum before running it:
REF=<release>  # a tag from github.com/EaseIT-cz/vornik/releases that ships quickstart.sh.sha256
base="https://raw.githubusercontent.com/EaseIT-cz/vornik/$REF/deployments/podman"
curl -fsSLO "$base/quickstart.sh" && curl -fsSLO "$base/quickstart.sh.sha256"
sha256sum -c quickstart.sh.sha256 && VORNIK_REF="$REF" bash quickstart.sh

# Or the convenience one-liner (pins the release tag baked into the script;
# set VORNIK_REF=main for bleeding-edge):
curl -fsSL https://get.vornik.io | bash
# Already inside a Vornik checkout? Use it as the build context instead:
VORNIK_SKIP_FETCH=1 VORNIK_DIR="$PWD" bash deployments/podman/quickstart.sh

    Check: the script ends with Vornik is up and ready., and:

    curl -fsS http://localhost:8080/readyz
# → {"status":"ready","checks":[{"name":"database","status":"ok"}]}

    If not: journalctl --user -u vornik -e — the loader names any config placeholder that is empty. Triage table: deployments/podman/README.md.

    Binaries land in ~/.local/bin (vornik, vornikctl). If vornikctl is not found, prefix commands with ~/.local/bin/ or fix PATH.

    Serving it over HTTPS (optional). On a host with a public DNS name and Caddy installed, add VORNIK_PUBLIC_HOSTNAME=<name> to the quickstart command. Caddy terminates TLS and adds no credential; people still sign in with their own key. It writes /etc/caddy/vornik.caddy with sudo, so ask your user first (ground rule 1). Steps and checks: deployments/podman/README.md, "HTTPS with the quickstart".

    From here on, start every command block with . ~/.config/vornik/shell-env.sh. The installer wrote it. It points vornikctl at the same config as the daemon and exports VORNIK_API_KEY, this install's operator key, which every API call below sends. Never print that variable (ground rule 2). Your shell may not keep variables between commands, so source it again in each block.

    A2. Connect an LLM (the setup API)¶

    The first-run web guide at http://localhost:8080/ui/setup and this API are the same flow; as an agent, drive the API. Ask your user for their OpenAI-compatible endpoint, model ID, and API key (rule 2), then:

    . ~/.config/vornik/shell-env.sh   # the install's config and operator key
SID=$(curl -fsS -H "X-API-Key: $VORNIK_API_KEY" -X POST http://localhost:8080/api/v1/setup/session \
  -H 'Content-Type: application/json' -d '{}' | sed -n 's/.*"id":"\([^"]*\)".*/\1/p')

# Validate first — this makes a live call to the provider:
curl -fsS -H "X-API-Key: $VORNIK_API_KEY" -X POST "http://localhost:8080/api/v1/setup/session/$SID/validate" \
  -H 'Content-Type: application/json' \
  -d '{"endpoint":"<ENDPOINT>","api_key":"<KEY>","model":"<MODEL>"}'

    Check: the response reports the endpoint and model reachable. Fix endpoint/key/model until it does — committing a broken config wastes a restart.

    . ~/.config/vornik/shell-env.sh   # the install's config and operator key
# Commit chat, then turn memory on with keyword search: it needs no
# embedding endpoint, and your agent's remember/recall (Runbook B) work at
# once. Add an embedding endpoint later from /ui/setup for semantic recall.
# SID is the session id from the block above; set it again if your shell
# did not keep it.
curl -fsS -H "X-API-Key: $VORNIK_API_KEY" -X POST "http://localhost:8080/api/v1/setup/session/$SID/commit" \
  -H 'Content-Type: application/json' \
  -d '{"endpoint":"<ENDPOINT>","api_key":"<KEY>","model":"<MODEL>"}'
curl -fsS -H "X-API-Key: $VORNIK_API_KEY" -X POST "http://localhost:8080/api/v1/setup/session/$SID/memory/commit" \
  -H 'Content-Type: application/json' -d '{"enabled":true,"keyword_only":true}'

    This writes the key to ~/.config/vornik/secrets/chat.env (the daemon sources that directory itself on start) and patches ~/.config/vornik/config.yaml. Manual fallback: set VORNIK_CHAT_API_KEY, CHAT_ENDPOINT, CHAT_MODEL in ~/.config/vornik/vornik.env.

    A3. First project + dispatcher¶

    The installer ships a personal assistant, assistant-project. Create it only if vornikctl project list does not show it:

    . ~/.config/vornik/shell-env.sh   # the install's config and operator key
vornikctl project list | grep -qw assistant-project || {
  vornikctl init project --template personal-assistant assistant-project \
    --config-dir "$HOME/.config/vornik/configs" &&
  vornikctl config reload    # loads the new project into the running registry
}
curl -fsS -H "X-API-Key: $VORNIK_API_KEY" -X POST http://localhost:8080/api/v1/setup/dispatcher \
  -H 'Content-Type: application/json' -d '{"project_id":"assistant-project"}'

    If init project refuses with "file already exists", a project made earlier from the same template holds its files: stop and show your user; do not pass --force.

    Check: vornikctl project list shows assistant-project, and the dispatcher commit returns "committed":true.

    A4. One restart, then verify¶

    Config from A2/A3 activates at process start. Ask the daemon to restart itself (call it on localhost only):

    . ~/.config/vornik/shell-env.sh   # the install's config and operator key
curl -sS -H "X-API-Key: $VORNIK_API_KEY" -X POST http://localhost:8080/api/v1/setup/apply
# → 202 {"applying":true}: the daemon restarts in about 30 s

    On 202, poll curl -fsS http://localhost:8080/readyz every 5 s until it answers ready. A refused connection is expected while the daemon restarts. Allow 120 s; if it is not ready by then, stop and show your user journalctl --user -u vornik -e.

    If the call is refused, its JSON code says what to do:

    code (HTTP status) you
    NO_SUPERVISOR (409), RESTART_NOT_WIRED (503) run systemctl --user restart vornik, then poll /readyz the same way
    JOB_RUNNING (409) a job is running: wait 30 s and call again, at most 10 times, then tell your user
    ALREADY_APPLYING (409) another apply will restart it: poll /readyz the same way and accept ready
    NOT_CONFIG_WRITER (409), CONFIG_LOCK (503), TASKS_UNREADABLE (500) stop and show your user the response; none should occur on a first install, so report it as a bug

    Then verify:

    . ~/.config/vornik/shell-env.sh   # the install's config and operator key
vornikctl doctor                              # feature readiness incl. chat
curl -fsS -H "X-API-Key: $VORNIK_API_KEY" http://localhost:8080/api/v1/setup/status
# → "fresh_install":false — onboarding is complete

    A5. First task¶

    The assistant's workflows research and write, so give it a small question. A bare greeting is refused with ROUTE_NO_FIT ("no workflow fits this task"); greetings belong in the chat below.

    . ~/.config/vornik/shell-env.sh   # the install's config and operator key
vornikctl task submit -p assistant-project \
  --prompt "In three sentences, explain what a local-first AI agent orchestrator is."
# Poll the returned task ID (first run pulls/warms the agent container — allow a few minutes):
vornikctl task get <taskId> -p assistant-project     # Status: COMPLETED
vornikctl task tail <taskId> -p assistant-project    # the answer, after "--- persisted ---"

    Check: task get shows Status: COMPLETED, and task tail prints the answer after --- persisted --- (task get does not show it). Show your user the answer and the chat UI: http://localhost:8080/ui/projects/assistant-project/chat.

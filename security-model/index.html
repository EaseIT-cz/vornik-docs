    Security model¶

    Last reviewed: 25 October 2026, against release 2026.10.8.

    This page describes what Vornik defends against, where its trust boundaries are, and the controls in place today, including what they do not cover. It applies to both editions; the few controls that exist only in the Enterprise Edition are marked (Enterprise). To report a vulnerability, see Security policy.

    Everything here is product behaviour. How a given installation is deployed (behind which proxy, with which model providers, on which host) is the operator's choice. Where that choice changes the security outcome, the page says so.

    What Vornik is, for this purpose¶

    Vornik is a daemon on a single host, with a control CLI (vornikctl). It:

    1. serves an HTTP API and a web console;
    2. runs AI agents in Podman containers, one container per task step;
    3. runs untrusted media (documents, images, audio, video) through tools in short-lived sandbox containers;
    4. talks to the outside: model providers, MCP servers, forges (GitHub and others), chat channels (Telegram, Slack, e-mail, web chat), and an optional third-party API gateway;
    5. serves other AI assistants (Claude Code, Codex, Hermes, …) as a companion: a memory, a delegate for privileged work, and, if the operator allows it, an administrator of its own workflows;
    6. asks a person to approve sensitive actions on a paired phone.

    The trust boundary contains the daemon, its database and its configuration directory. Everything else is treated as potentially hostile: network clients, agent containers, model output, tool and web content, chat users, connected assistants, and upstream services.

    Threat model¶

    In scope¶

    Actor Can Concern
    Network attacker reach the HTTP port read or change data without a key; spoof a forwarding header; exhaust resources
    API client with a key call the API reach another project's data; widen its own reach
    Agent container run model-directed code escape its workspace; read another project's data; reach the host, the internet or the daemon's credentials; make the daemon run a program
    Prompt-injected content arrive in a web page, mail, ticket, document or tool result steer an agent into exfiltration or an unwanted write
    Chat user write to a channel trigger work they are not allowed; read a task's error text or secrets
    Connected assistant (companion or agent-admin key) call Vornik's tools read raw private data behind a summary; act outside its grant; approve its own requests
    Holder of a stolen approver device or its cookie open approval pages approve sensitive actions
    Hostile upstream (model, MCP server, forge, gateway, vendor OAuth server) shape responses crash or hang the daemon; redirect a request with secrets; plant instructions
    Crafted upload be extracted or rendered read local files, fetch URLs, or exhaust the host through a parser

    Out of scope¶

    • Physical access to the host, and root on the host.
    • Escapes from Podman or the kernel. Vornik hardens what it starts but does not defend against a container-runtime escape.
    • Network-level floods (DDoS). There are per-request limits, not traffic shaping.
    • People who may write the configuration directory. Operator configuration is inside the trust boundary (see Residual risks).

    Trust boundaries¶

     network client ──▶ HTTP API / console ──▶ database (trusted)
 (key, session,          │
  approver device)       ▼
                    Vornik daemon ──────────▶ model providers, MCP servers,
                    (scheduler,                forges, chat platforms, gateway
                     executor, guards)         (outbound, untrusted responses)
                     │            │
         podman run  │            │ podman run (one-shot, no network)
                     ▼            ▼
             agent container   sandbox tool run
             (untrusted)       (untrusted input)

 connected assistant ──MCP──▶ companion endpoint (scoped key) ──▶ daemon
 paired phone ──────────────▶ approval pages (device-bound session)

    Controls¶

    HTTP API and console¶

    • Authentication on every route except liveness/readiness probes and /metrics; the quickstart configuration requires an API key. Credentials are checked by one ordered chain (session, signed webhook, database keys, static keys) that stops at the first refusal. Key comparison is constant-time.
    • Admin class is decided once per request. One decision function governs the operator surface (configuration, reloads, daemon-wide repairs); a second decides who may read error text and logs (operator, scrubbed, or denied, with denied as the default).
    • Per-project scoping on every project resource. A project-scoped key that asks for another project's object gets "not found", not "forbidden", so existence does not leak.
    • Agent keys reach only the agent route set, on every listener (TCP and the unix socket), and cannot post as the operator.
    • Request bodies are size-capped and strictly decoded. The configuration dump redacts every credential-shaped field; a test plants a marker in every string field of the configuration and requires each credential-shaped one to come back redacted.
    • Same-origin checks on every state-changing console request, through one shared gate; Secure cookies on HTTPS.
    • A content-security policy on every console response. It admits only this origin for scripts, and an inline script only by the SHA-256 of its exact text, computed at start from the embedded templates (a console whose hashes cannot be computed does not start). There is no 'unsafe-inline' or 'unsafe-eval' for scripts, no inline event handler, and htmx neither evaluates attributes nor runs scripts from swapped HTML. What it does not cover: a hash admits that exact text anywhere on the console, so an injection could replay one of the console's own scripts in another place; inline styles remain allowed.
    • Real client IP behind a proxy is taken from the configured header only when the immediate peer is in the configured trusted-proxy list; otherwise the peer address is used. A trusted-proxy entry wider than one address logs a warning at startup. Rate limits and login lockouts key on this value.
    • Managed hosting (hosting.mode: managed, for hosted instances; off by default) splits the daemon into a public listener and an operations listener. The public listener refuses every admin-class key, in any header it can be presented in, before routing, serves no metrics, and treats an administrator's browser session there as the instance owner, who may use a short, closed list of operator surfaces (the project wizard, the template gallery, MCP OAuth connections, the operator audit) and no other; administrator access exists only on the operations listener, which must bind a loopback or private address. Managed mode refuses to start with authentication off. It also requires the per-IP request limit and a narrow trusted-proxy list, starts no stdio MCP server, limits model endpoints to public addresses (except the listed model gateway names, which may resolve to private addresses but never to loopback or metadata addresses), and limits every MCP server it dials to public addresses and same-host redirects.

    Configuration integrity¶

    • Every request-derived name joined into the configuration or workspace tree (project, swarm, workflow, schema, file) is cleaned and confined under its root by one path helper; separators, ., .. and empty names are refused.
    • Every read-modify-write of the daemon configuration file goes through one file lock, so two subsystems cannot overwrite each other's changes.
    • Applying a configuration change records the deployed file it replaces first, so every apply can be rolled back; an apply that cannot record it is refused. No request commits to git on the host.
    • The configuration assistant sees a redacted snapshot: secret-named values and lists are withheld, and a file it cannot screen fully (a secret reached through a YAML alias, more than one YAML document) is refused rather than shown.

    Identity, chat channels and who sees what¶

    • People are user accounts; API keys, chat identities (Telegram, Slack, e-mail) and devices map to accounts. Single sign-on via OIDC is (Enterprise).
    • Chat channels have sender allowlists that fail closed when empty (a Slack direct message is gated by the sender list, not the channel list).
    • Non-operators see scrubbed task text. Task errors, status text, input prompts and output excerpts reaching a chat user who is not an admin-linked operator in a private chat are passed through a scrubber that withholds secret-bearing lines and replaces e-mail addresses, home paths, IP addresses and the host name. The same rule applies to the chat model's status tools.
    • Every AI-generated chat reply carries the EU AI Act Art 50(1) disclosure for its channel; a turn whose disclosure cannot be delivered is refused.

    Approvals and approver devices¶

    • Sensitive actions (an assistant's new connection or credential, a widening of its reach, a proposed write) are approved on a paired phone, not in the requesting channel. Pairing is started by the operator from vornikctl.
    • A device's session cookie rotates on every decision; a copied cookie dies at the device's next approval, and a browser riding a device's approvals raises an alert. Restoring a device is an operator action and is alerted.
    • An approval binds to the hash of the exact arguments shown, computed over a canonical form that refuses duplicate keys, so the approver cannot be shown one thing and approve another. Choice cards accept only a choice.
    • Approval notices pushed to a channel carry no content, only a link.

    Agent containers¶

    • Every container runs with all Linux capabilities dropped, no-new-privileges, a non-root user, and labels for discovery and reaping. Only the pinned agent image may be started. The scripts that drive the container are owned by root, so an agent cannot rewrite them.
    • Read-only root and a PID limit (runtime.agent_read_only_root, runtime.agent_pids_limit; off by default, always on in managed hosting). With the read-only root, an agent writes only its mounts, /tmp, /var/tmp and its home (disk-backed volumes removed with the container) and two small bounded tmpfs (/run, /dev/shm); the PID limit bounds a fork bomb. A periodic sweep removes containers, and their volumes, that a crash left behind, only once their task has finished. Without the settings, the PID limit is the host podman's own default.
    • Network policy per role. The default is daemon-only: no network device at all, with the daemon reachable over a unix socket for tools and model calls. Roles that need the internet opt in to an isolated egress namespace; host networking is available but discouraged.
    • Per-task credentials. Each task step gets its own short-lived, project-bound key. If minting it fails, the step is refused; it never falls back to a static or provider key.
    • Workspaces are git worktrees. Daemon git commands pin the git directory and work tree, read a global git config composed by the daemon (hooks, filter drivers and core.hooksPath dropped), and never read state an agent can write. Warm containers mount no project. A task the daemon cannot give a worktree fails before any container starts.
    • Inputs are staged only from the task's own project; outputs are harvested through one pinned directory handle, so a running agent cannot swap files under the daemon. Symlinks that leave the workspace are refused.
    • Credentials stay out of containers. Third-party API credentials live in the gateway, MCP credentials in the daemon, and an agent's tool arguments carry none.

    No daemon surface chooses a program¶

    • Exactly one part of the daemon may start a process, and it runs a closed set of program kinds: the pinned agent image (with an allowlist of flags), container control verbs, git under a registered workspace root, the git HTTP backend, and a stdio MCP server or CLI model provider that only the configuration loader can define. Each kind parses its argv against a closed grammar before a process exists.
    • No request, UI form or configuration write from a request may add or alter a stdio MCP server. Host diagnostics (podman, systemd, journal) run only in vornikctl doctor on the host, never in the daemon.
    • An architecture test fails the build when a daemon-linked package gains the ability to start processes outside that one place.

    Untrusted media: sandbox tool runs¶

    • Extraction (PDF, OCR, audio, video), document rendering, and voice (speech-to-text, text-to-speech) run as one-shot containers of the pinned agent image: no network, read-only root, a small tmpfs, a pids limit, all capabilities dropped, inputs mounted read-only, and per-feature memory, CPU, time and input-size limits. Inputs over the limit are refused before a container starts. Output is bounded by a per-file size limit plus a once-a-second sample, not a disk quota.
    • Renderers cannot read local files, fetch, or run script. ffmpeg reads only the uploaded file, through a file-only protocol list and a short list of permitted formats.
    • Archive extraction is guarded against zip bombs, oversized expansion, too many entries, and symlinks that escape the destination.

    Prompt injection and untrusted content¶

    • Third-party content is scanned on the way to a model, including MCP tool results, for injection attempts, credential leakage and encoded payloads. Findings name the rule that produced them.
    • Content from outside is wrapped in an untrusted-content envelope whose close tag the model can see; the wrapper fails closed on malformed or over-encoded input.
    • Taint lineage. Each autonomous step records whether it consumed untrusted content. In enforce mode, a write by a tainted task parks for operator review with its sources attached. The default mode is advisory.
    • Memory ingest gates run on every deposit: secret scan (a mostly redacted "secret dump" is rejected outright), per-project deny patterns (substring, not regex), optional injection detection, dedup and size checks. A memory firewall attaches sensitivity, role, purpose and expiry policy to chunks and audits every retrieval decision. A connected assistant's deposits land unverified and low-confidence, and its corrections cannot overrule an operator's.
    • Learned skills are never drafted from goals whose words came from a third party (webhook, forge, chat or A2A).

    Secrets¶

    • A secret detector (known token shapes plus an entropy heuristic) runs at every persistence and display boundary: task results, tool audit, container logs, artifacts, transcripts, chat notices and memory. Credential-shaped findings are redacted; inbound webhooks with a secret are blocked. Heuristic findings are counted but no longer rewrite stored artifacts, because they produced no true positives in production.
    • Results are validated before redaction, so redaction cannot corrupt a result into a schema failure; everything stored or forwarded is the redacted form.
    • Outbound tool arguments are scanned too. For an assistant-administered project a credential-shaped value in a tool argument blocks the call; a refusal names the field, never the value.
    • vornikctl secrets scan-history rescans stored history (tool audit, step prompts, transcripts, task messages) and redacts what it finds.
    • Credentials an assistant provides are sealed at rest with a key file the operator must back up; the doctor checks that the key opens them.

    Outbound connections and SSRF¶

    • Every outbound client has a timeout and a read cap.
    • A dial guard refuses loopback, link-local, private, special-use and reserved ranges, including IPv6 transition forms that embed a blocked IPv4 address (NAT64, 6to4, IPv4-compatible), and the cloud instance-metadata addresses (IPv4 and the IPv6 ones in private ranges) even where private ranges are allowed. A hostname is judged by the address it resolves to, and guarded clients ignore proxy environment settings. One list decides for every guard. An operator-listed allowed host is an explicit vouch and bypasses the list, metadata addresses included. Operator-listed private ranges are allowed only where a feature needs them.
    • Redirects that would carry secrets are refused; gateway redirects stay on the same origin.

    MCP servers¶

    • OAuth 2.1 for remote MCP servers: discovery, dynamic client registration, PKCE, resource indicators, refresh. A stored grant is bound to its resource audience, so a token minted for one path is not presented to a sibling path. Token requests do not follow redirects. Write scopes for daemon-wide servers must be named in configuration, and the CLI says what it withheld.
    • Every stored OAuth token is sealed at rest with the secret store key file, bound to its project, server and field, so a value copied to another row does not open. A token found unsealed in the database is never served, and the doctor reports it.
    • A server can be required to declare its tools; it is then refused when it advertises a mutating tool that is not in its allowlist.
    • A configuration reload that removes a server cannot be undone by a connection that was still dialling.

    Assistants: the companion, the broker and agent administration¶

    • A companion key is bound to one project, optionally to a list of workflows and a budget, and may use only the companion endpoint. A memory key can be minted without any task tools.
    • Broker projects let an assistant ask for privileged work (read my mail, check my calendar) without ever holding the credentials or seeing raw data. A broker workflow takes typed, bounded inputs and returns one schema-checked, scanned document; error text is reduced to a closed class.
    • Writes are proposals. A broker workflow may only propose a write; a person approves the exact arguments; a single worker performs it once and never retries, recording "unknown" when the outcome is uncertain. Writes are off until the operator enables them. Standing grants for repeated writes are bounded in days, uses and number.
    • Agent administration lets an assistant build projects and workflows in its own namespace. Its key lives in a file only the user can read, read by a bridge command, so no assistant configuration holds it. For an assistant that can run shell commands, connecting checks that Vornik runs as a different OS user. Every credential and every widening of reach is approved on the phone; the assistant never sees a credential. Refused calls are recorded and shown.
    • Completion pushes to an assistant carry only ids and closed states, and refuse loopback, link-local and unlisted private addresses.

    Data protection¶

    • Retention windows per data class, with floors for audit evidence (tool audit is kept at least six months, as the AI Act requires deployers to keep logs) and an AI-disclosure log that is never pruned.
    • Data-subject rights: a register of whom a record concerns, identity-verified access and portability reports, erasure with a preview, and a breach ledger with the 72-hour clock. Exclusive records are deleted; records that also concern other people are redacted, not destroyed, and re-embedded. Erasure of a person's turns in multi-person conversation transcripts is partly built; until it is complete, such a request is reported as not fully actioned rather than marked done.
    • AI Act Art 5: the vision agent refuses identification, emotion inference and inference of sensitive characteristics.

    Supply chain and releases¶

    • Release and Community-export builds start from empty module, build and tool caches and run go mod verify before building. govulncheck and CodeQL run in CI.
    • Only the pinned agent image may run. An image provenance record lets the daemon compare running images to a release; a packaged host without the record reports that it cannot verify rather than passing. Locally built images are recorded by source commit only, because their digests differ per host.
    • The Community export is scanned for leaked private material before publication.

    Availability¶

    • Request size caps, per-project rate limits on internal endpoints, bounded queues that drop and count rather than block, bounded mail polling, and panic recovery around provider SDK calls.
    • Log forwarding with TLS and CA pinning is (Enterprise).

    Residual risks¶

    1. Operator configuration is trusted. Whoever can write the configuration directory can point Vornik at any model, MCP server or channel. Protect it like /etc.
    2. Model endpoints may be private. Configured chat and embedding endpoints dial through the guard with private ranges allowed, so a local or LAN model server works: link-local addresses (the cloud metadata service) and redirects to another host are refused, but a configured endpoint can reach any loopback or private address. Use network-level egress filtering if configuration is partly delegated.
    3. Rate limiting is per feature, not global. The general API has no per-IP request limit; it relies on a small set of authenticated keys. The IP-based defences are only as good as the trusted-proxy list.
    4. Prompt injection is mitigated, not solved. Scanning detects and wrapping isolates, but a model can still be misled; the structural defences are scoped keys, schema-bound outputs, approvals for writes and, in enforce mode, taint parking.
    5. Approvals are only as good as the approver. An approver who approves without reading defeats the gate; nothing in software prevents that.
    6. Sandbox output is bounded by sampling, so a run can overshoot its output cap by up to one second of writes.
    7. Machine-readable marking of AI-generated content (EU AI Act Art 50(2)) is designed but not yet built; it is due by 2 December 2026. Synthetic voice replies will be off by default until they can be watermarked.
    8. Image signatures are not verified. Pin images by digest or use a private registry with content trust.

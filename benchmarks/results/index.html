    Agent quality — a 4B-active open-weight model on one GPU (2026-10-31)¶

    Result. On one RTX 3090 workstation, gemma-4-26b-a4b completed 89 to 90 of 90 software tasks through Vornik's multi-agent dev-pipeline. The electricity for a full run cost €1.34 to €1.40. The bench's price list puts the same tokens on a hosted model at about $20.

    Measured on 2026.10.7-94-g3246baad0, which is part of 2026.11.1. The run was made twice: once without container hardening (OFF) and once with a read-only agent root filesystem and a 2,048-process limit (ON).

    OFF ON
    run slots passed (30 tasks × 3 repeats) 90 of 90 89 of 90
    acceptance suites passed (12 graded) 9; 3 did not compile 11; 1 did not compile
    expected files produced 76 of 90 79 of 90
    schema conformance (share of steps whose output matched the required structure) 0.965 0.973
    tool-call validity 1.000 1.000
    steps with no output 3.0% 3.5%
    tokens per task 324,067 325,975
    wall time per run (median) 5.1 min 4.6 min
    run window 9.94 h 9.63 h
    energy, model host 3.87 kWh (389 W average) 3.69 kWh (383 W average)
    electricity cost 34.18 CZK (€1.40) 32.58 CZK (€1.34)
    priced cost on a hosted model $20.88 $19.75

    Setup. Model: gemma-4-26b-a4b (26B parameters, about 4B active per token), GGUF Q4_K_M, served by llama.cpp with native tool calls, 131,072-token context, about 141 tokens/s decode. Vornik's daemon, harness and agent image were built from one commit. The task set is 20 dev-pipeline and 10 simple-workflow tasks, each run 3 times.

    Energy. Metered at the model host's wall socket over each run window. The meter covers the model host only, not the machine running Vornik. Priced at 8.83 CZK/kWh (36.26 euro cents): Eurostat's Czech household electricity price for H1 2026, all taxes and charges included (nrg_pc_204), at the Czech National Bank rate of 30 October 2026. Hardware cost is not included.

    What the numbers show.

    • Vornik carries a small model to completion. Malformed output was caught and re-asked (about one schema retry per run). Every step that produced nothing was recovered by a retry. No tool call was malformed.
    • Finishing is not the same as being right. Task success says the pipeline finished. Only 4 of the 30 tasks carry an acceptance suite, so the correctness signal is 9 of 12 (OFF) and 11 of 12 (ON): mostly right, not always, on a small sample.
    • The hardening costs nothing measurable. The one ON slot that failed was a model loop and two step timeouts; the daemon log of the whole arm has no read-only filesystem or process-limit error. One slot in 90 is not distinguishable from noise (Fisher's exact test, p = 1.0). Energy per hour differed by 1.5%.

    What this does NOT establish.

    • No ranking against other models or the 2026.9.0 row. The model, the hardware and the harness version all differ, and no comparison was pre-registered.
    • No noise floor. One run per arm, three repeats per task.
    • One OFF slot was run twice. The harness refused to start it because the previous task's failure left files in the workspace (a known harness gap), so it never reached a container. It was re-run on the same commit and configuration, outside the metered window, and passed.
    • Not independently reproducible. As for the 2026.9.0 row, the task set and its answer key are not published.
    • The electricity price is a national household average. A different tariff changes the cost in proportion.

    Agent quality — 2026.9.0 (first scored arm)¶

    30 software tasks through a multi-agent dev-pipeline swarm, scored against an operator-reviewed answer key. It measures the control logic's decisions (what the lead granted, whether roles followed their output schemas, whether agents called tools correctly), not retrieval.

    Release Tasks Task success Schema conformance Tool-call validity Steps with no output Cost/task
    2026.8.9-70-g5d247f72 (shipped as 2026.9.0) 30 100.0% 0.985 1.000 9.7% $0.29

    Same arm: 667,801 tokens and 62.4 tool calls per task, 0 escalations, 0 schema retries, $8.79 in total.

    Read the step figure with the success figure. Task success is 100%, but 14 of 144 terminal steps (9.7%) produced no output: 8 hit the iteration cap, 4 entered a degenerate tool loop, 2 failed. Recovery absorbed them.

    The model is part of the result. Qwen/Qwen3.8-27B-FP8, self-hosted on one machine. Over about 244,000 tool calls on two deployments, it entered identical-repeat tool loops 26 times as often as a mix of larger hosted models (0.52% of calls against 0.02%), and changed approach after a nudge 36% of the time against 82%. A self-hosted 27B is what someone running Vornik at home has, so this row describes the harder case; a large hosted model behind the same control logic sees the lower rate. The comparability key pins the model, so an arm on another model cannot silently replace this row.

    Cost corrected on 2026-09-19. First published as $0.74 per task and $25.23 in total: the model was missing from the pricing table, so calls were billed at the default $1.00/$3.00 per million tokens instead of $0.35/$2.75. The corrected figures come from the arm's recorded tokens (22,353,287 prompt, 351,933 completion). They are an upper bound: this path did not report prompt-cache reads, and a later pass on the same model served 79.5% of prompt tokens from cache at a tenth of the input rate. Quality figures are unaffected.

    What this row does NOT establish.

    • No pass or fail. bench agent gate refused a verdict: resolving a 5-point effect at the inherited σ of 0.0604 needs 12 paired tasks; this arm has 5, which resolve 7.6 points.
    • No trend. It is the first scored arm.
    • No noise floor for this task set. The σ comes from an earlier 3-task measurement of a different set.
    • Not independently reproducible. The task set and answer key are not published.

    Provenance. The daemon binary and agent image are recorded by content digest in the arm key, and batches that disagree on any axis are not merged. Arms recorded before 2026-08-29 carry no agent-image identity (the executor discarded it), so they cannot serve as a baseline. This is the first arm with real image provenance.

    Reproduce. Run against a bench daemon, never production: the run bulk-writes and clears the store.

    # Mint the token against the bench daemon:
#   VORNIK_API_URL=<daemon> vornikctl companion grant \
#       --project bench --client claude-code --memory-all
export VORNIK_URL=<your-bench-daemon>
export VORNIK_COMPANION_TOKEN=<companion key with memory_read + memory_write>
export VORNIK_BENCH_DSN=postgres://<user>:<pass>@<host>:5432/<your-bench-db>?sslmode=disable

curl -sLO https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned/resolve/main/longmemeval_oracle.json
vornikctl bench memory run --system vornik --dataset longmemeval \
    --dataset-path ./longmemeval_oracle.json \
    --dataset-sha256 821a2034d219ab45846873dd14c14f12cfe7776e73527a483f9dac095d38620c \
    --database <your-bench-db> --i-know-this-wipes <your-bench-db> \
    --tier2-only --accept-unverified-path \
    --our-extraction-model "<the embedder the daemon reports>" \
    --recall-method context-assembly \
    --max-items-per-category 20 --max-tokens 4096 \
    --run-dir ./run-$i          # repeat for i in 1 2 3
vornikctl bench memory aggregate ./run-*
    • The harness reads VORNIK_URL and VORNIK_COMPANION_TOKEN. vornikctl's own VORNIK_API_URL and VORNIK_API_KEY are a different pair; setting only those aims the run at http://localhost:8080, which on a single host is production. The database guard is the last line of defence.
    • --our-extraction-model must match what the daemon embeds with, or the run is refused. Read it from whoami (embedder); the key uses <provider>/<model>@<dimensions>d, for example openai/qwen3-embedding:0.6b@1024d. Leaving it unset is what made the 2026-09-08 run's key partial.
    • Set memory.reranker.enabled: false on the daemon under test. --tier2-only stops requesting the reranked path but cannot disable it, and refuses the run if a rerank happened. An LLM reranker reorders results between identical runs.

    Dataset: LongMemEval v1-cleaned (xiaowu0162/longmemeval-cleaned, September 2025), longmemeval_oracle.json, sha256 821a2034d219ab45846873dd14c14f12cfe7776e73527a483f9dac095d38620c. Budget: max_tokens=4096. Judge: none.

    LongMemEval — judged accuracy (tier 1) and the judge's noise floor¶

    A judged number needs the judge's own variance first, or a "win" cannot be told apart from the judge disagreeing with itself. Ten identical runs, same items, same models, warm corpus:

    Metric Mean sd Min Max Narrowest defensible gate (3σ)
    judged accuracy 0.8241 0.0340 0.7500 0.8750 ±0.1020
    context recall 0.9764 0.0059 0.9722 0.9861 ±0.0176
    context precision 0.9410 0.0000 0.9410 0.9410 exact
    MRR 0.9917 0.0108 0.9792 1.0000 ±0.0323

    n=10 runs × 24 temporal-reasoning items, key a2fd4d245b21. Judge: gemma4:31b. Answerer: gpt-oss:120b, a different model family, so the judge does not grade its own output. Both open-weight, version-pinned and served by one provider (Ollama Cloud); a multi-provider router would add variance to the number being measured.

    • Accuracy moved between 0.750 and 0.875 with nothing changed but the models' sampling: 3 of 24 items flipped. A tier-1 gate needs ±10.2 points, wider than most real improvements. That is why tier 2 leads: on the same runs, context precision was exactly constant.
    • Context recall varies here (sd 0.0059) but not in tier 2. These runs use the system as shipped, with the LLM reranker in the path; tier 2 uses the reranker-free path.
    export VORNIK_BENCH_LLM_URL=https://ollama.com/v1
export VORNIK_BENCH_LLM_KEY=<your key>
for i in $(seq 1 10); do
  vornikctl bench memory run --system vornik --dataset longmemeval \
    --dataset-path ./longmemeval_oracle.json \
    --database <your-bench-db> --i-know-this-wipes <your-bench-db> \
    --answer-model gpt-oss:120b --judge-model gemma4:31b \
    --category temporal-reasoning --max-items 24 --max-tokens 4096 \
    --run-dir ./jv-$i
done
vornikctl bench memory aggregate ./jv-*

    About 4.5 minutes per run on the reference deployment; the first run is slower because it ingests the corpus.

    Comparison: hindsight 0.9.0, same items, same budget¶

    Same machine, same six temporal-reasoning items, each system as it ships (own reranker on), both cold (store or bank cleared before every run):

    System Context recall Context precision MRR Runs
    Vornik 1.0000 ±0.0000 0.9444 ±0.0000 0.9444 ±0.0481 n=3
    hindsight 0.9.0 1.0000 ±0.0000 0.6806 ±0.0833 0.7292 ±0.1250 n=4
    • Recall ties at 1.000. This oracle subset has about three sessions per item; the full longmemeval_s has 38 to 62, where recall should separate the systems.
    • Vornik's retrieved set is tighter and better ordered (precision 0.944 against 0.681, MRR 0.944 against 0.729); hindsight reaches the same recall by returning more.
    • hindsight varies between runs (precision sd 0.083, MRR sd 0.125, MRR 0.667 to 0.917 over four runs) because an LLM consolidates its memories at ingest, so its corpus differs each time. A single hindsight run cannot be quoted; a gate on it would need ±0.375 MRR. Vornik's ingest is chunk and embed, with no model deciding what is stored.
    • Caveats. n=6, one ability: a smoke-scale baseline, not a ranking. Both arms are retrieval_path_unverified (rerankers on). hindsight's extraction model was pinned to google/gemma-4-26b-a4b-it, with its bundled local embedder and reranker; Vornik used its configured local embedder. Without deleting hindsight's bank between runs its precision fell from 0.806 to 0.639 on an identical repeat.

    LongMemEval — the six-item warm axis (closed)¶

    Closed on 2026-08-21. Until 98037e34 the harness did not clear the store its flag (--i-know-this-wipes) promised to clear, so runs repeated against an already-ingested, warm corpus. Every run since is cold. The missing clear moved scores: on three runs of the same 120 items, admitted deposits went 426 → 426 → 209 as the store filled, and judged accuracy moved from 0.692 to 0.750 after a manual wipe. Warm figures understate the system by an amount nobody has bounded, because a deduplicated item loses the haystack it is scored against.
